# Data Observability – Olist E-Commerce Data Platform

## 1. Overview

This document describes the data observability layer implemented in the Olist E-Commerce Data Platform.

The objective is to monitor data quality over successive pipeline executions, maintain a history of quality metrics, detect potential data degradation, and visualize historical trends through an interactive dashboard.

The observability layer complements the existing data quality validation system. Instead of validating data only during a single execution, it tracks quality indicators over time.

## 2. Architecture

The observability layer is integrated into the existing data pipeline orchestrated by Apache Airflow.

The pipeline execution order is:

```text
Bronze → Silver
     |
     v
Data Quality Validation
     |
     v
Quality Metrics Tracking
     |
     v
dbt Build and Tests
     |
     v
Historical Metrics (CSV)
     |
     v
Streamlit Dashboard
```

### Main components

| Component | Responsibility |
|---|---|
| Python ETL | Transforms raw Bronze data into Silver data |
| Data Quality Validation | Generates data quality checks and reports |
| Metrics Tracking | Extracts and stores quality metrics |
| Anomaly Detection | Compares consecutive runs to identify potential degradation |
| Apache Airflow | Orchestrates pipeline execution |
| dbt | Builds analytical models and executes data tests |
| Streamlit | Displays historical quality metrics |
| Plotly | Generates interactive visualizations |

## 3. Historical Metrics Tracking

### Implementation

The script `src/observability/track_quality_metrics.py` extracts relevant metrics from the data quality report generated by:

`data/reports/data_quality_report.json`

The extracted metrics are appended to:

`data/reports/quality_metrics_history.csv`

Each row represents one pipeline quality report.

### Tracked metrics

**General quality indicators**

- Total number of checks
- Passed checks
- Checks requiring review
- Failed checks

**Payment metrics**

- Non-positive payment values

**Product metrics**

- Zero product dimensions
- Negative product dimensions
- Missing product dimensions

The tracked dimensions include:

- Product weight
- Product length
- Product height
- Product width

**Review metrics**

- Duplicate review IDs
- Null review IDs

**Category metrics**

- Number of unmatched product categories

### Historical storage

The CSV file provides a simple historical record of quality indicators.

It allows comparisons between successive pipeline executions and serves as the data source for the monitoring dashboard.

The current implementation appends one metrics record each time the tracking script is successfully executed.

## 4. Anomaly Detection

### Implementation

Anomaly detection is implemented in:

`src/observability/detect_quality_anomalies.py`

The script reads the historical metrics CSV and compares the two most recent executions.

### Detection rules

The current implementation identifies:

| Condition | Severity |
|---|---|
| Increase in non-positive payments | WARNING |
| Increase in invalid or missing product dimensions | WARNING |
| Increase in null review IDs | WARNING |
| Increase in unmatched categories | WARNING |
| Increase in failed checks | CRITICAL |
| Increase in checks requiring review | WARNING |
| Decrease in passed checks | WARNING |
| Increase in duplicate review IDs | INFO |

Duplicate review IDs are treated as informational because duplicate values in `review_id` alone do not necessarily indicate invalid records. The composite key `(review_id, order_id)` is unique in the current dataset.

### Execution

Run the anomaly detection module with:

```bash
python -m src.observability.detect_quality_anomalies
```

At least two historical runs are required for comparison.

If no degradation is detected, the script displays:

```text
No quality degradation detected.
```

The current implementation uses rule-based comparisons between consecutive runs. It does not yet implement statistical anomaly detection, adaptive thresholds, or long-term trend analysis.

## 5. Airflow Integration

The observability tracking process is integrated into the Airflow DAG:

`olist_data_pipeline`

The execution order is:

1. `bronze_to_silver`
2. `data_quality`
3. `track_quality_metrics`
4. `dbt_build`

The `track_quality_metrics` task executes:

```bash
python -m src.observability.track_quality_metrics
```

This task runs after data quality report generation to ensure that the report exists before metrics are extracted.

Airflow provides technical monitoring through:

- DAG execution status
- Individual task status
- Task start and end timestamps
- Task execution duration
- Execution logs

The current DAG uses manual triggering (`schedule=None`).

## 6. Monitoring Dashboard

### Technologies

- Streamlit
- Pandas
- Plotly

### Implementation

The dashboard is implemented in the root-level file:

`app.py`

It reads historical metrics directly from:

`data/reports/quality_metrics_history.csv`

### Dashboard features

**1. Latest Pipeline Quality Report**

Displays the latest recorded values:

- Total checks
- Passed checks
- Checks requiring review
- Failed checks

**2. Quality Checks Evolution**

An interactive line chart displays the evolution of:

- PASS checks
- REVIEW checks
- FAIL checks

**3. Detailed Quality Metrics**

Allows users to select an individual metric and visualize its evolution over time.

**4. Historical Quality Metrics**

Displays the historical records stored in the CSV file.

**5. Dashboard Refresh**

A refresh button clears the Streamlit data cache and reloads the latest historical metrics.

### Run the dashboard

Activate the Python virtual environment and execute:

```bash
python -m streamlit run app.py
```

The dashboard is available locally at:

`http://localhost:8501`

## 7. Execution and Validation

The observability implementation has been validated through several pipeline executions.

The historical tracking script successfully records new metrics after each execution.

The anomaly detection logic has been tested using synthetic test cases covering:

- Stable metrics
- Increasing non-positive payments
- Increasing unmatched categories
- Newly failed checks
- Informational increases in duplicate review IDs

The test suite includes five anomaly detection tests.

The full project test suite currently contains 27 passing tests.

The Airflow pipeline has also been executed successfully with all four tasks completing in the `success` state.

## 8. Current Limitations and Future Improvements

The current implementation provides a first version of a data observability layer.

Potential improvements include:

- Tracking pipeline execution duration automatically in a dedicated historical table.
- Adding freshness and data volume monitoring.
- Introducing configurable anomaly thresholds.
- Implementing statistical anomaly detection.
- Adding automated alerts for critical quality degradation.
- Improving dashboard filtering and visualization.
- Introducing persistent monitoring storage beyond CSV files.
- Configuring scheduled Airflow execution instead of manual triggering.

## 10. Conclusion

The observability layer extends the Olist data platform beyond one-time data validation.

By combining historical quality metrics, rule-based anomaly detection, Airflow execution monitoring, and an interactive Streamlit dashboard, the platform provides visibility into data quality across successive pipeline runs.

This implementation establishes a foundation for more advanced data observability capabilities in future iterations.
